> **作者**：Ivy Zhang

上一篇我们把 MCP Server 跑起来了：STDIO、Streamable HTTP、SSE，也看过 Tool、Resource 和 Prompt 的代码。代码能跑是个好消息，但在真实项目里，代码能跑通常只是故障单刚刚学会走路。

这篇继续往下挖一个更实际的问题：**MCP 到底解决了什么？**

答案不是“它让模型变聪明了”，也不是“它消灭了所有 JSON”。MCP 解决的是一组软件工程问题：工具由谁拥有、客户端如何发现能力、不同 Agent 如何复用同一个服务、协议和业务如何隔离，以及测试团队如何对这条调用链建立可验证的边界。

如果把模型比作一个会写计划但经常忘记带工牌的同事，MCP 做的不是给他加智商，而是给他配了门禁、通讯录、工单系统和审计记录。至于他会不会把生产库当测试库，仍然需要我们测试工程师拦住他。

## 一、先把上一篇的结论校准一下

上一篇提到 Function Calling 的 JSON 胶水代码，这个判断方向没错，但“Function Calling 已经过时”就说得太满了。

Function Calling 仍然适合这些场景：

- 工具数量很少，并且只服务于一个 Agent 应用。
- 工具和业务逻辑必须在同一个进程中运行。
- 团队希望完全控制模型请求、工具执行和错误重试。
- 你只是需要让模型调用一个查询函数，不需要独立的能力发现和跨客户端复用。

MCP 的价值在工具逐渐变成基础设施以后才明显：测试平台、代码仓库、CI、日志系统和缺陷系统都有自己的负责人，不能每接一个 Agent 就复制一套函数和 schema。此时问题从“模型能不能调函数”变成了“多个客户端如何稳定地使用同一套工具服务”。

### 1. MCP 没有改变模型的输入格式

MCP Server 和模型通常不是直接对话。典型链路是：

```text
用户 -> Host（Cursor / Codex / 自建 Agent）
     -> MCP Client
     -> MCP Server
     -> 工具、资源或提示模板
```

Host 仍然要把可用工具转换成模型供应商理解的格式。模型仍然可能把 `run_id` 写成 `runtime_id`，也仍然可能在需要字符串时传一个数字。MCP 不会替模型做语义推理，也不会替服务端完成授权。

它改变的是责任边界：**工具服务不再和某个模型请求绑死，Agent 也不再需要把所有业务函数复制进自己的代码库。**

### 2. MCP 的中立描述是什么样的

MCP 使用 JSON-RPC 作为消息格式。下面是一个简化的 `tools/list` 返回结果。它是 MCP Server 的能力描述，不是 OpenAI 或 Anthropic 的专属 schema。

## 二、MCP 真正解决的四个工程问题

### 1. 工具的所有权和生命周期

Function Calling 很容易把工具定义写在 Agent 项目里。第一周看起来很快，第三个月就会出现这样的目录：

```text
agent-a/tools.py
agent-b/tools.py
agent-c/integrations/github.py
agent-d/legacy_tools/ci.py
```

它们都在查同一个测试平台，但返回字段不同、超时时间不同、鉴权方式不同。某次接口改名以后，大家开始在群里玩“谁的 CI 先红”。

MCP 把工具变成一个有独立生命周期的服务。它可以单独发布版本、配置权限、记录调用、回滚变更，也可以被多个 Agent 使用。对测试工程师而言，这意味着工具服务本身可以有自己的契约测试和灰度策略，而不是跟着每个 Agent 一起发布。

### 2. 能力发现，而不是把工具清单写死

传统 Function Calling 通常在每次模型请求里传入工具定义。MCP Client 可以在建立会话后调用 `tools/list`，发现当前 Server 实际暴露的能力。

这解决了一个经常被低估的问题：**配置文件和真实服务能力不一致。**

不过动态发现并不等于“任何工具都应该暴露给模型”。生产环境需要在 Client 或网关侧做 allowlist、权限过滤和版本约束。动态是为了减少同步成本，不是为了让模型逛完公司的全部系统。

### 3. 工具、数据和工作流的边界

如果所有东西都做成 Tool，模型想看日志也得调用一个“读取日志工具”，想拿提示模板也得调用一个“返回字符串工具”。这会让只读数据、可执行动作和流程约束混在一起。

MCP 至少把三种能力区分开：

- **Tool**：明确的动作，可能有副作用。查询测试结果也可以是 Tool，触发重跑、创建缺陷更需要权限和确认。
- **Resource**：按 URI 获取的上下文数据，通常是只读的。Server 仍然需要自己做访问控制和脱敏。
- **Prompt**：可复用的交互模板，适合把团队的排障步骤、审查格式和报告结构固化下来。

这不是为了凑“三件套”，而是为了让调用链更容易审计：谁读了什么数据，谁执行了什么动作，谁提供了什么工作流模板，记录可以分开看。

### 4. 传输层和业务层解耦

同一套工具业务逻辑，开发阶段可以通过 STDIO 让 IDE 启动，部署后可以通过 Streamable HTTP 提供给远程 Agent。传输变化不应该迫使你重写测试查询、构建查询和日志读取逻辑。

这也是 MCP 比“在 Agent 里加一个 HTTP 路由”更有价值的地方：它把会话初始化、能力发现、消息格式和传输约定也纳入了边界。当然，HTTP 服务依旧需要 TLS、认证、Origin 校验、限流和审计，协议不会替你填安全评审表。

## 三、Resource 不是“让模型随便读文件”

上一篇里提到动态 Resource 和 Roots，这里需要把边界讲准确。

Resource Template 可以描述一类 URI，例如 `audit://apps/{service}/critical`。Client 可以根据模板构造具体 URI，Server 再决定如何解析和返回数据。但这不代表模型自动拥有任意路径的读取权限，也不代表 Roots 会自动替所有工具建立沙箱。

**Roots 是 Client 提供给 Server 的工作区边界提示，Server 必须自行执行边界校验。** 如果一个 Tool 接受文件路径，仍然要用 `resolve()`、白名单目录和权限检查阻止目录穿越。安全边界不能靠模型“自觉”，也不能靠注释表达。

下面用一个测试报告 Resource 演示正确的边界做法：只允许读取配置的报告目录，并且在返回前截断内容。

<div class="code-fold" markdown="1">
<p class="code-title">Resource 的路径边界和内容截断</p>

```python
from pathlib import Path

from mcp.server.fastmcp import FastMCP

mcp = FastMCP("test-report-reader")
REPORT_ROOT = Path("/var/lib/test-reports").resolve()


def safe_report_path(report_name: str) -> Path:
    candidate = (REPORT_ROOT / report_name).resolve()
    if REPORT_ROOT not in candidate.parents or candidate == REPORT_ROOT:
        raise ValueError("report path is outside the configured report directory")
    if candidate.suffix != ".json":
        raise ValueError("only JSON reports are readable")
    return candidate


@mcp.resource("test-report://runs/{report_name}")
def read_report(report_name: str) -> str:
    path = safe_report_path(report_name)
    return path.read_text(encoding="utf-8")[:20_000]


if __name__ == "__main__":
    mcp.run(transport="stdio")
```

## 四、不要把“参数自愈”当成生产策略

原稿里有一个很诱人的说法：参数错了就把错误文本返回给模型，让模型自己修正。这种方式在 Demo 里很有戏剧效果，在生产里却不能当成默认策略。

原因很简单：

- 类型转换可能改变业务含义。`"001"` 是否等于整数 `1`，需要业务决定。
- 自动重试可能重复执行有副作用的操作。
- 错误文本可能泄露内部路径、权限信息或堆栈细节。
- 模型修正成功不代表原始请求是安全的。

更可靠的做法是：**先做 schema 校验，再做业务校验；只对明确安全的输入做有限归一化；对有副作用的调用要求幂等键或人工确认。**

下面是一个轻量的 Tool 边界示例。它不会把错误伪装成成功，也不会无限重试。

<div class="code-fold" markdown="1">
<p class="code-title">Tool 的输入校验、幂等和可审计返回</p>

```python
import ipaddress
from dataclasses import dataclass

from mcp.server.fastmcp import FastMCP

mcp = FastMCP("network-change-tools")


@dataclass(frozen=True)
class BlockRequest:
    ip: str
    request_id: str


def validate_request(ip: str, request_id: str) -> BlockRequest:
    if not request_id or len(request_id) > 80:
        raise ValueError("request_id is required and must be shorter than 80 chars")
    address = ipaddress.ip_address(ip)
    if address.is_private or address.is_loopback:
        raise ValueError("refuse to block private or loopback addresses")
    return BlockRequest(ip=str(address), request_id=request_id)


@mcp.tool()
def block_ip(ip: str, request_id: str) -> dict:
    """提交一次可审计、可幂等的封禁请求。"""
    try:
        request = validate_request(ip, request_id)
    except ValueError as exc:
        return {"ok": False, "error": "invalid_request", "message": str(exc)}

    # 真实实现会在这里调用防火墙服务，并以 request_id 做幂等键。
    return {
        "ok": True,
        "request_id": request.request_id,
        "ip": request.ip,
        "status": "accepted",
    }


if __name__ == "__main__":
    mcp.run(transport="stdio")
```

## 五、测试工程师应该怎么测 MCP

MCP 的测试不能只点一下聊天框，看模型有没有说“已经完成”。至少要把链路拆成四层：协议、能力、业务和模型协作。

### 1. 协议层：先确认服务能正常说话

协议层关注初始化、能力协商、工具列表、资源列表、错误响应和会话重连。它不需要模型参与，可以用固定 JSON-RPC 请求验证。

<div class="code-fold" markdown="1">
<p class="code-title">协议层断言：能力发现和错误响应</p>

```python
def assert_tool_contract(tools: list[dict]) -> None:
    names = {tool["name"] for tool in tools}
    assert "query_test_run" in names

    query = next(tool for tool in tools if tool["name"] == "query_test_run")
    schema = query["inputSchema"]
    assert schema["type"] == "object"
    assert "run_id" in schema["required"]


def assert_invalid_request(error: dict) -> None:
    assert error["code"] == -32602
    assert "message" in error
```

### 2. 能力层：检查描述是否足够准确

模型是否能正确选择工具，首先取决于工具名称、描述和参数说明。测试这些字段时，不要只断言字段存在，还要检查危险动作是否标明副作用、必填参数是否有示例、返回结构是否稳定。

一个好用的工具描述应该让测试人员在不看实现代码的情况下回答：

- 这个工具什么时候应该调用？
- 它会不会修改数据？
- 失败后能不能安全重试？
- 结果里哪些字段是稳定契约？

### 3. 业务层：把 MCP 当成普通服务测试

MCP 不会让数据库、CI 或防火墙变得更可靠。业务层仍然要测权限、超时、空结果、脏数据、重复调用、上游 500 和部分成功。工具函数的单元测试、服务的集成测试和端到端调用测试，仍然各有职责。

### 4. 协作层：验证“先读再写”，而不是验证模型会背台词

对于“先读日志、再触发动作”的流程，重点是验证状态转换和证据链：

1. 没有读取 Resource 时，Tool 是否拒绝执行或要求确认。
2. 读取到无关日志时，模型是否不会凭空提取攻击源。
3. Tool 执行失败时，是否不会被模型包装成成功。
4. 同一个 `request_id` 重试时，服务是否保持幂等。
5. 超过上下文限制时，日志是否分页或截断，并保留关联 ID。

这才是 MCP 场景下测试工程师的优势：我们不只关心“模型答得像不像”，还关心这条链路是否可观测、可重放、可拒绝、可回滚。

## 六、传输方式怎么选

上一篇已经给过三种传输的代码，这里只补充选择依据。

### STDIO：本地工具优先

适合 IDE 本地启动、个人开发环境和不希望开放网络端口的工具。优点是部署简单，权限继承本地进程；缺点是无法直接被远程 Agent 使用。stdout 只能输出协议消息，日志写 stderr，这条规矩足以让很多 Demo 第一次启动就学会谦虚。

### Streamable HTTP：团队共享和远程服务

适合 CI、测试平台、代码扫描和企业内部工具网关。它可以被多个 Client 使用，也更容易接入认证、限流、监控和服务发现。生产环境不要只把 localhost 用 ngrok 暴露出去就算上线，至少要有 TLS、身份认证、Origin 校验、超时和审计。

### SSE：旧客户端迁移

SSE 适合作为历史 HTTP+SSE transport 的兼容层。新服务优先考虑 Streamable HTTP，避免以后同时维护两套 endpoint、两套会话语义和两套故障排查手册。

## 七、MCP 不解决什么

工程讨论里把边界说清楚，往往比列优点更有用。MCP 不会自动解决这些问题：

1. **不会提高模型推理准确率**：模型仍可能选错工具或编造参数。
2. **不会自动完成安全治理**：认证、授权、脱敏、审计和沙箱需要服务端实现。
3. **不会替你设计业务幂等**：重跑测试、创建缺陷、修改防火墙规则都需要业务层保证。
4. **不会替你做质量判断**：工具能返回测试失败，不代表模型就能准确归因。
5. **不会消除供应商差异**：Host 仍然要把 MCP 能力适配到具体模型 API。
6. **不会让糟糕的工具描述变好**：工具名和 schema 写得含糊，换成 MCP 也只是把含糊标准化了。

## 八、结语：MCP 是边界协议，不是魔法棒

MCP 最值得采用的地方，不是它让模型获得了“调用函数”的超能力，而是它把一堆容易互相污染的责任拆开了：

- Server 负责业务能力和安全边界。
- Client 负责协议会话和能力发现。
- Host 负责模型适配、用户交互和审批。
- 测试工程师负责验证契约、风险、异常和全链路证据。

当工具只有一两个时，直接 Function Calling 可能更省事；当工具开始跨项目复用，开始需要独立发布、权限治理和多 Agent 接入时，MCP 才真正显示出价值。

所以更准确的结论是：**MCP 没有终结 Function Calling，它把 Function Calling 从业务应用里搬到了一个更适合治理的位置。**

这也是测试工程师最容易切入的地方：先别急着让模型封禁 IP、重跑全量回归。先把工具契约、Resource 边界、失败语义、幂等策略和审计证据测清楚。能拒绝错误请求的 Agent，通常比只会说“已完成”的 Agent 更接近生产。
